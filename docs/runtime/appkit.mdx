---
title: AppKit
description: Build native macOS windows and controls from JavaScript with Bun.AppKit
---

`Bun.AppKit` creates real AppKit windows and controls from JavaScript on macOS. There is no web view and no bundled UI toolkit: a `Button` is an `NSButton`, a `TextField` is an `NSTextField`, and layout is Auto Layout through `NSStackView`.

<Warning>This API is experimental and macOS-only. It may change in future releases.</Warning>

```ts counter.ts icon="/icons/typescript.svg"
import { app, Window, VStack, Text, Button } from "bun:appkit";

let count = 0;
const label = new Text({ text: "Count: 0", font: { size: 24, weight: "bold" } });
const button = new Button({
  title: "Increment",
  onClick() {
    count++;
    label.text = `Count: ${count}`;
  },
});

const stack = new VStack({ spacing: 12, padding: 20 });
stack.append(label, button);

const win = new Window({ title: "Counter", width: 280, height: 140, content: stack });
win.show();
```

```sh
bun counter.ts
```

The process stays alive while a window is open and exits when the last window closes, the same way it does for a server or an open socket. Nothing is linked into `bun` for this: AppKit is loaded with `dlopen` the first time you use it, so programs that never touch `Bun.AppKit` pay nothing.

`Bun.AppKit` and `import ... from "bun:appkit"` are the same namespace.

### How it is put together

The module is two layers, and both are yours to use.

The floor is [`objc`](#the-objective-c-bridge), a bridge to the Objective-C runtime: every class, selector and protocol that Foundation, AppKit, QuartzCore and Metal register, under Apple's own names (`objc.classes.NSAlert`, `panel.beginSheetModalForWindow_completionHandler_(win.native, fn)`), every `NS_ENUM` and `NS_OPTIONS` of those frameworks by name (`objc.enums.NSWindowStyleMask.titled`, `objc.enums.MTLPixelFormat.bgra8Unorm`), exported constants, blocks made from functions, out-parameters, and classes defined in JavaScript for delegates, data sources and targets. It converts arguments and results by the method's type signature, turns an `NSException` into a JavaScript error, and manages retain and release for you. Someone with Apple's documentation open can predict what any call does.

`Window`, `VStack`, `Button`, `Table`, the menu bar and the rest of this page are written in JavaScript on that bridge; nothing in them is out of reach of a program that uses `objc` directly. Each one makes its `NSWindow`, `NSStackView` or `NSButton`, wires the control's target and action or a delegate to a JavaScript-defined object, and lays out with `NSLayoutConstraint`. So every element has `.native`, the very object it made, as an `objc` handle; the props that can be read from that object read it live (`button.title` after `button.native.setTitle_("x")` is `"x"`); a prop that names an enumeration accepts every member by Apple's name; and nothing is create-only. What stays native (Rust) is small: loading the frameworks, running Bun's event loop inside AppKit's, the application lifecycle (start, quit, App Nap), [`MetalView` and `gpu`](#metal), and the bridge's message, block and class machinery.

## The `app` object

```ts
import { app } from "bun:appkit";

app.name = "My Tool"; // used in the standard menus ("About My Tool", "Quit My Tool"); defaults to the executable's name
app.activationPolicy = "regular"; // "regular" (Dock icon + menu bar), "accessory" (no Dock icon), "background"
app.badge = "3"; // Dock badge, null to clear
app.keepAlive = true; // starts the app and keeps the process running with no window open (menu bar utilities)
app.menu = [
  { title: app.name, items: [{ title: `Quit ${app.name}`, key: "q", action: "terminate:" }] },
  {
    title: "File",
    items: [
      { title: "New Window", key: "n", onClick: () => new Window({ title: "Untitled" }).show() },
      "separator",
      { title: "Close", key: "w", action: "performClose:" },
    ],
  },
  {
    title: "Edit",
    items: [
      { title: "Copy", key: "c", action: "copy:" },
      { title: "Paste", key: "v", action: "paste:" },
    ],
  },
];

app.windows; // open Window objects
app.isDark; // whether the app's appearance is dark (false until the app has started)
app.hasDisplay; // false over ssh, on CI agents and in sandboxes; does not start the app
app.isRunning; // whether the app has started
app.activate(); // start if needed and bring to front
app.hide();
app.quit(); // same path as Cmd-Q, see below

app.on("beforequit", e => e.preventDefault()); // Cmd-Q, the Dock's Quit, logout, app.quit(); veto by preventing default
app.on("reopen", () => {}); // Dock icon clicked while running
```

The application starts lazily when the first `Window` is created, `app.keepAlive` is set to `true`, or `app.activate()` is called (`app.quit()` before that point is just `process.exit()`). Set `app.activationPolicy` before that if you do not want a Dock icon. Starting does not activate the app or take focus: the first `win.show()`, `win.focus()` or `app.activate()` does. Reading `app.hasDisplay`, `app.isDark` or any other property never starts it. While a window is open or `app.keepAlive` is `true` the process holds an `NSProcessInfo` activity so App Nap does not throttle its timers and I/O in the background; with neither, macOS may nap it like any other idle app.

By default the menu bar has the standard application, Edit, View and Window menus, so text editing shortcuts, full screen and Cmd-Q work without any setup. Assigning `app.menu` replaces the whole menu bar with your menus; the first one is always the application menu (macOS titles it with the app's name whatever its `title`), so start with that and include the standard items you want to keep. `app.menu = null` restores the default bar. The bar is built out of `NSMenu` and `NSMenuItem` through the [`objc` bridge](#the-objective-c-bridge) once the application starts (`objc.classes.NSApplication.sharedApplication().mainMenu()` is that object), and rebuilt on every assignment; reading `app.menu` gives back the array you assigned, since the functions in it cannot be read back out of an `NSMenu`. To change one item later without rebuilding the bar (check it, retitle it), `app.menuItem(item)` returns the `NSMenuItem` built for that item object of `app.menu` (or, for one of its menus, the main-menu item holding it), and `setState_` / `setTitle_` on it take effect at once; it is `null` for an object that is not in the installed bar. `setEnabled_` there only lasts while the menu has `autoenablesItems` off, since AppKit re-validates targeted items whenever a menu opens; otherwise set `enabled` in the spec. A menu item takes either an `onClick` callback or an `action`: a function (the same thing), or the name of an Objective-C action method such as `"copy:"`, `"paste:"`, `"undo:"`, `"selectAll:"`, `"performClose:"`, `"performMiniaturize:"`, `"toggleFullScreen:"`, `"hide:"` or `"terminate:"`. A function is target/action on a script object; a selector is sent with no target down the responder chain (the focused view, its window, the application), which is how the built-in menus work, and AppKit enables such an item only while something in the chain implements the method, so any action a responder has (including one on a class from `objc.defineClass`) can go there. Then `key` with optional `shift` / `option` / `control` / `command` (default `true`) modifiers, `enabled`, `checked`, and `submenu`. `"separator"` (or `"-"`) draws a line. The standard bar also registers its Window menu with AppKit as the one that lists open windows and its Services submenu as the Services menu; a custom bar that wants either can call `setWindowsMenu:` / `setServicesMenu:` on the application through `objc`.

`app.quit()`, Cmd-Q, the Dock's Quit and a logout all take one path. `beforequit` listeners run first; calling `event.preventDefault()` or returning `false` cancels the quit (a listener that throws is reported like an uncaught error and neither cancels the quit nor hides another listener's veto). Then every window that is still open (hidden, minimized and non-closable ones too) is asked through its `shouldClose`, oldest first, and closed if it agrees; the first `false` cancels the quit and later windows are left alone. If none refused, the process exits the way `process.exit()` does: `process.on("exit")` handlers run, the exit code is `process.exitCode`, and `app.keepAlive`, listening servers and pending timers do not hold it. From `app.quit()` that happens at the next turn of the event loop, so code after the call in the same function still runs; from Cmd-Q, the Dock or a logout it happens before AppKit's own terminate returns. Once a quit has been accepted, further requests do not run `beforequit` again. To only close the windows and keep running, veto and close them yourself: `app.on("beforequit", e => { e.preventDefault(); for (const w of app.windows) w.close(); })`.

## Windows

```ts
const win = new Window({
  title: "Inspector",
  width: 480, // content size in points; default 480 x 320
  height: 320,
  x: 100, // screen coordinates, bottom-left origin; omit both to center
  y: 100,
  minWidth: 200, // also maxWidth, minHeight, maxHeight
  minHeight: 100,
  resizable: true, // also closable, minimizable (default true)
  titlebarTransparent: false,
  fullSizeContent: false,
  titleHidden: false,
  restoreName: "inspector", // AppKit saves and restores the frame under this name
  background: "windowBackground",
  alpha: 1,
  content: someView,
  visible: false, // default true: shown as soon as it is created
});

win.show(); // orders front and activates the app
win.hide();
win.center();
win.focus();
win.close(); // idempotent
win.content = otherView; // replace the root view
win.width = 600; // every option above is a property afterwards, and assigning it changes the window
win.snapshot(); // Uint8Array PNG of the window's content view (null before the window has a size)

win.visible;
win.closed; // once closed, assigning any property throws ERR_INVALID_STATE
win.key; // has keyboard focus
win.resizable = false; // read from and written to the window's styleMask, like closable and minimizable

win.onClose = () => {}; // after the window closed, by the user, close() or a quit
win.shouldClose = () => confirmDiscard(); // close button and quit; return false to keep the window open (close() does not ask)
win.onResize = ({ width, height }) => {}; // user resizes, zoom, full screen, content-driven growth; not win.width = ...
win.onMove = ({ x, y }) => {}; // user moves; not win.x = ... or center()
win.onFocus = () => {};
win.onBlur = () => {};
```

A `Window` is written in JavaScript on the [`objc` bridge](#the-objective-c-bridge) like the views are: the class makes the `NSWindow` (`win.native` is that very object), its events are an `NSWindowDelegate` defined in JavaScript (`shouldClose` is `windowShouldClose:`, `onClose` `windowWillClose:`, `onResize`/`onMove` `windowDidResize:`/`windowDidMove:`, `onFocus`/`onBlur` `windowDidBecomeKey:`/`windowDidResignKey:`), and `title`, `width`/`height`, `x`/`y`, `alpha`, `visible`, `key`, the style-mask flags, `titlebarTransparent`, `titleHidden`, `restoreName` and the size limits (`contentMinSize` / `contentMaxSize`) read the window itself, so a change made through `win.native` shows in them; `background` reads back what you assigned. `win.native` stays the `NSWindow` after the window closes, so an `onClose` handler can still ask it anything.

The root view is pinned to the window's edges. A `VStack` root hugs the top and lets a child with `grow` (or a `ScrollView`, `TextEditor`, `Table`) take the remaining height. Content that needs more room than the window has makes the window wider or taller; content that fits leaves the size alone. `minWidth` / `maxWidth` / `minHeight` / `maxHeight` bound user drags, `win.width = n`, the initial size, and content-driven growth where the content can be compressed (a fixed `height` on a child yields to `maxHeight`; required spacing and padding do not, and grow the window to fit). Lowering a limit under the current size resizes the window to it, and if a minimum exceeds a maximum the minimum wins.

## Views

Every view is a class you construct with an optional props object and then mutate through accessors. Containers (`VStack`, `HStack`, `ZStack`, `Group`, `ScrollView`, `SplitView`) additionally have `children`, `append(...views)`, `insertBefore(view, ref)`, `removeChild(view)` and `replaceChildren(...views)`. A view has at most one parent; `view.remove()` detaches it. `insertBefore` and `replaceChildren` with a view that is already a child move it in place, so a focused text field keeps its focus through a reorder; a call that is rejected (a reference view that is not a child, a view that belongs to another container) changes nothing. `view.parent`, `view.window` and `view.frame` are read-only; `frame` is `{ x, y, width, height }` in the parent's coordinates and lays the window out first, so it reflects every change made so far (all zeros while the view is not in a window). `view.snapshot()` returns a PNG of just that view.

"Readable state" props read the live value back from the control, so `field.value` reflects what the user typed and `button.title` reflects a `setTitle:` sent through `button.native`. Every other getter returns the last value you set, or the prop's default (the value in parentheses above, or the `@default` in the type definitions) while it is unset; assigning `null` puts a prop back to its default. Setting a value from code (`field.value = "x"`, `slider.value = 3`, `checkbox.checked = true`, `win.width = 500`) does not fire that view's `onChange` or the window's `onResize` / `onMove`.

Everything in this table except `MetalView` is written in JavaScript on the [`objc` bridge](#the-objective-c-bridge): the class makes the `NSButton`, `NSTextField` or `NSStackView` (`view.native` is that very object) and reads it back for the props in the last column, and the common props, `frame` and `snapshot` are sends and `NSLayoutConstraint`s on that object for every view. A `VStack` is an `NSStackView` whose children are its arranged subviews (`align: "fill"` adds a width constraint per child; `grow` ties the growing children's lengths together in ratio), a `ZStack` a plain `NSView` with each child pinned to its edges, a `ScrollView` an `NSScrollView` over a flipped `NSClipView`, a `SplitView` an `NSSplitView` whose panes' holding priorities follow `grow`. A control's `onClick` / `onChange` / `onSubmit` are its target and action, so they run synchronously inside the click or keystroke, whether the user's or `click()`'s; a text field's `onChange`, `onFocus` and `onBlur` are its `NSTextFieldDelegate`, a text editor's `onChange` its `NSTextViewDelegate`. A `Table` is a view-based `NSTableView` whose data source and delegate is one script object: AppKit asks it for the row count and for a cell view as each row scrolls into sight, so `rows` stay in JavaScript and a long array costs nothing until it is looked at; `onSelect` is that delegate's `tableViewSelectionDidChange:` and `onActivate` the table's double action. Props that name an enumeration (`bezelStyle`, `textAlign`, `scaling`) take every member of Apple's by its name without the prefix, the full name, or the number from `objc.enums`, and read back the short name. `bezelStyle` for one is `"push"` for `NSBezelStylePush` (or `"NSBezelStylePush"`, or `objc.enums.NSBezelStyle.push`) and reads back the number for a value with no current name. The usual button roles are plain props: `keyEquivalent: "\r"` makes the window's default button (accent-coloured, answers Return), `bordered: false` draws like a link, `bezelStyle: "toolbar"` is a toolbar button and `hasDestructiveAction: true` marks a destructive one.

A `TextField`'s `onBlur` (and, with `continuous: false`, the pending `onChange`) fires whenever editing ends, including when your own code ends it: hiding or removing the field, replacing the window's content, closing the window (ahead of the window's `onClose`). It is then delivered as that call returns, after the change it made is complete, so the handler may freely read and change the field, its container and the window. Return in a text field calls `onSubmit`; a field without one presses the window's default button (the one whose `keyEquivalent` is `"\r"`) instead, as a native dialog does.

`Radio` buttons that are direct children of the same container act as one group: turning one on (by click or from code) turns the others in that container off, and only the one that was clicked fires `onChange`. Radios in different containers are independent.

`click()` on a `Button`, `Checkbox`, `Radio` or `Switch` performs a real click (`performClick:`), which is how tests drive the UI without a mouse.

In a `VStack`, children stretch to the stack's width by default (`align: "fill"`); buttons keep their natural width. In an `HStack` children are vertically centered. `align` accepts `fill leading center trailing top bottom firstBaseline lastBaseline` (each the `NSLayoutAttribute` that means that on the stack's axis, so `bottom` on a `VStack` reads back as `trailing`), or any `NSLayoutAttribute` by name or number, read back by its name; `distribution` accepts `fill fillEqually fillProportionally equalSpacing equalCentering gravity` or any `NSStackViewDistribution` name or number. `padding` reads back as the stack's `{ top, left, bottom, right }` edge insets whichever form set it. A `Group`'s `title` set to `""` hides the title area; setting one again shows it at the top unless a position was chosen through `.native`. A title or text that does not fit is truncated rather than making the window wider.

### Colors and fonts

Colors are strings: `"#rgb"`, `"#rgba"`, `"#rrggbb"`, `"#rrggbbaa"`, `"rgb(r, g, b)"` / `"rgba(r, g, b, a)"`, or a system color name that follows the user's appearance and accent settings: `label secondaryLabel tertiaryLabel quaternaryLabel text placeholder link separator accent control controlText controlBackground windowBackground underPageBackground textBackground selectedContentBackground clear black white gray red orange yellow green mint teal cyan blue indigo purple pink brown`.

`font` is a point size or `{ size?, weight?, design?, italic? }`. `weight` is CSS-style `100`-`900` or one of `ultralight thin light regular medium semibold bold heavy black`; `design` is `default`, `monospaced`, `rounded` or `serif`; `size: 0` or omitted means the standard control size.

## Metal

`MetalView` is an `MTKView` in the view tree, and `gpu` is a small typed API over the system's default Metal device: compile Metal Shading Language from a string, create buffers and textures from typed arrays, build render and compute pipelines, encode a frame, and read results back. It is enough to draw custom content in a window, render offscreen, or run a compute kernel, without any native add-on. There is no scene graph; you write the shaders.

```ts triangle.ts icon="/icons/typescript.svg"
import { Window, MetalView, gpu } from "bun:appkit";

const lib = gpu.library(/* metal */ `
  #include <metal_stdlib>
  using namespace metal;
  struct Out { float4 position [[position]]; float4 color; };

  vertex Out vs(uint id [[vertex_id]], constant float& angle [[buffer(0)]]) {
    const float2 corners[] = { float2(0, 0.8), float2(-0.7, -0.6), float2(0.7, -0.6) };
    const float3 colors[] = { float3(1, 0, 0), float3(0, 1, 0), float3(0, 0, 1) };
    float2 p = corners[id];
    float2x2 rotate = float2x2(cos(angle), sin(angle), -sin(angle), cos(angle));
    return { float4(rotate * p, 0, 1), float4(colors[id], 1) };
  }
  fragment float4 fs(Out in [[stage_in]]) { return in.color; }
`);
const pipeline = gpu.renderPipeline({ vertex: lib.function("vs"), fragment: lib.function("fs") });

const view = new MetalView({
  grow: 1,
  clearColor: "#1e1e1e",
  onFrame(frame, { time }) {
    frame.renderPass(view).pipeline(pipeline).vertexBytes(0, Float32Array.of(time)).draw(3);
  },
});
new Window({ title: "Triangle", width: 400, height: 400, content: view });
```

### Frames

Every frame, `onFrame(frame, { time, dt, width, height })` receives a `GpuFrame`, which is one Metal command buffer with a chained encoding API. `frame.renderPass(view)` starts a render pass into the view's drawable and only works inside that view's `onFrame`; the first pass into the view each frame clears it to `clearColor`, later ones draw on top (pass `{ clear }` to choose). `renderPass({ color: texture, clear, depth })` renders offscreen instead. `computePass()` and `blit()` start the other two kinds of pass, and starting a pass ends the previous one. Bindings follow Metal's argument tables: `vertexBuffer(0, buf)` is `[[buffer(0)]]` in the vertex function, `fragmentTexture(1, tex)` is `[[texture(1)]]` in the fragment function, and `vertexBytes` / `fragmentBytes` / `bytes` copy up to 4 KB of uniforms inline without a buffer.

When `onFrame` returns, the frame is committed and the drawable presented for you unless you already called `frame.commit()`. If `onFrame` throws, the frame is dropped and the error is reported like any other uncaught exception in a callback. If the GPU later fails to run a `MetalView` frame (a faulting shader, a timeout), that is reported the same way, as a `GpuExecutionError`, before that view's next `onFrame`, unless your code kept the frame and read its `gpuStatus` or `error` first; frames from `gpu.frame()` report only through `gpuStatus`, `error` and `commitAndWait()`. All encoding happens synchronously on the main thread inside `onFrame`; the GPU then executes the frame asynchronously.

Pipelines, buffers and textures are meant to be created once and reused across frames. `buffer.write()`, `buffer.read()`, `texture.replace()` and `texture.readPixels()` wait for any committed frame that used the resource to finish first, so they never race the GPU; the cost is that writing one buffer every frame makes the CPU wait for the previous frame. For a few KB of per-frame data use `vertexBytes` / `fragmentBytes` / `bytes`, which copy inline; for more, rotate between two or three buffers (`buffer.inFlight` says whether a write would wait).

For a depth buffer, ask for one in the pass: `frame.renderPass(view, { depthFormat: "depth32float" })`. The view allocates a depth texture the size of its drawable the first time and keeps it; pipelines used in that pass declare the same `depthFormat`, and `frame.depthStencil(gpu.depthStencil({ compare: "less" }))` turns the depth test on.

With a display attached and `running: true` (the default) the view drives `onFrame` from the screen's refresh at `preferredFPS`. With `running: false`, or in a headless process, nothing happens until you call `view.draw()`, which runs one frame synchronously; that is also how tests drive it. `onResize({ width, height })` reports the drawable size in pixels whenever it changes. The view's output is colour-matched as sRGB, the same as colours given to other views.

### Offscreen rendering

`gpu.frame()` makes a frame that is not tied to a view. Render into a texture, wait for the GPU, and read the pixels back:

```ts
const target = gpu.texture({ width: 256, height: 256, format: "rgba8unorm", usage: ["render", "read"] });

gpu
  .frame()
  .renderPass({ color: target, clear: [0, 0, 0, 0] })
  .pipeline(
    gpu.renderPipeline({ vertex: lib.function("vs"), fragment: lib.function("fs"), colorFormats: ["rgba8unorm"] }),
  )
  .vertexBytes(0, Float32Array.of(0))
  .draw(3)
  .end()
  .commitAndWait(); // blocks until the GPU is done

const rgba = target.readPixels(); // Uint8Array, 256 * 256 * 4 bytes, rows top to bottom
await Bun.write("triangle.rgba", rgba);
```

`commit()` returns immediately; afterwards `frame.gpuStatus` moves from `"running"` to `"completed"` or `"failed"` (with the reason in `frame.error`) without blocking. `commitAndWait()` blocks until the work has finished and throws a `GpuExecutionError` if the GPU reported one. A pipeline's `colorFormats` must match the textures it renders into (`"bgra8unorm"`, the `MetalView` format, is the default). Up to 32 frames can be open (created and not yet committed) at once; `gpu.frame()` throws past that, so commit frames as you go rather than collecting them.

A vertex function that takes `[[stage_in]]` needs a `vertexLayout` on the pipeline: `{ stride, attributes: [{ format, offset }] }` describes vertex buffer 0, and an array of those describes one vertex buffer per element, with `[[attribute(n)]]` numbers counting on across them (or given as `index`).

### Compute

```ts
import { gpu } from "bun:appkit";

const lib = gpu.library(`
  #include <metal_stdlib>
  using namespace metal;
  kernel void twice(device float* values [[buffer(0)]], uint i [[thread_position_in_grid]]) {
    values[i] *= 2.0;
  }
`);
const twice = gpu.computePipeline(lib.function("twice"));

const input = new Float32Array([1, 2, 3, 4, 5, 6, 7, 8]);
const buffer = gpu.buffer(input); // "shared" storage: one allocation seen by CPU and GPU

gpu.frame().computePass().pipeline(twice).buffer(0, buffer).dispatch(input.length).end().commitAndWait();

const output = new Float32Array(buffer.read().buffer); // 2, 4, 6, 8, ...
```

`dispatch(threads, threadsPerGroup?)` takes a total grid size in one, two or three dimensions (`1024`, `[width, height]`). Left out, the threadgroup size is the pipeline's `maxTotalThreadsPerThreadgroup` for a one-dimensional grid, and `threadExecutionWidth` wide by as many rows as that maximum allows for two or three dimensions, capped at the grid size. `buffer.read()` after `commitAndWait()` (or after `commit()`, where it waits by itself) sees the kernel's writes.

### Shaders and errors

`gpu.library(source)` compiles MSL at run time. A compile error throws a `GpuCompileError` whose `message` is the compiler log with line and column numbers; asking a library for a function it does not have throws a `TypeError` that lists the ones it does have, and so does handing `renderPipeline` a kernel or `computePipeline` a vertex function (`fn.type` says which kind a function is). Creating a render or compute pipeline can also throw `GpuCompileError` when the functions do not link (for example a fragment input the vertex function does not produce). `GpuExecutionError` is for failures on the device: it is thrown by `commitAndWait()`, returned by `frame.error`, thrown by `gpu.buffer()` / `gpu.texture()` when Metal cannot allocate, and reported for `MetalView` frames as described above.

### Packing uniforms with `gpu.struct`

Metal lays structs out with its own alignment rules (a `float3` takes 16 bytes, a `float4x4` is 16-byte aligned), so hand-packing a `Float32Array` is error-prone. `gpu.struct` computes the layout, prints the matching MSL declaration, and packs JavaScript values into bytes you can pass to `vertexBytes` or write into a buffer:

```ts
const Uniforms = gpu.struct({ mvp: "float4x4", tint: "float3", time: "float" }, "Uniforms");

Uniforms.size; // 96
Uniforms.fields.tint; // { offset: 64, size: 16, align: 16, ... }
Uniforms.msl; // "struct Uniforms {\n  float4x4 mvp;\n  float3 tint;\n  float time;\n};"  (paste into the shader)

frame.vertexBytes(1, Uniforms.pack({ mvp: modelViewProjection, tint: [1, 0.5, 0], time }));

// Reuse one allocation across frames:
const scratch = new ArrayBuffer(Uniforms.size);
Uniforms.pack({ time }, scratch); // fields you leave out stay as they were
```

Supported types are `bool`, `uchar4`, `short`, `ushort`, `half`, `half2`, `half3`, `half4`, `int` to `int4`, `uint` to `uint4`, `float` to `float4`, `float2x2`, `float3x3` and `float4x4`. Vectors and matrices take arrays or typed arrays; matrices are column-major. This part is pure arithmetic and works without a GPU.

### Availability

`gpu.available` is `false` on Macs without a Metal device, which in practice means virtual machines and some sandboxes. Every other `gpu` member then throws `TypeError: Metal is not available`, and a `MetalView` still takes part in layout but never calls `onFrame`. Check it once at startup if your program can do something useful without the GPU. Buffers and textures default to `"shared"` storage, which JavaScript can read and write directly; `"private"` storage is GPU-only and is filled with `frame.blit().copyBuffer(...)` or by rendering into it. Buffers and textures report their size to the garbage collector; `destroy()` releases one right away when you know you are done with it.

## Event loop

AppKit must run on the main thread, which is also the JavaScript thread. Bun keeps its own event loop as the outer loop and, only while the app is running, waits for I/O inside AppKit's event dispatch instead of directly in `kevent`. A file descriptor becoming ready or a timer coming due wakes that wait by itself, so there is no polling interval: timers, `fetch`, sockets, `Bun.serve`, subprocesses, `Worker` messages and file watchers all keep running while windows are open, and UI callbacks (`onClick`, `onChange`, window events) run in the same phase of the tick as socket callbacks, with microtasks drained before control returns to AppKit.

Two consequences:

- A long synchronous piece of JavaScript freezes the UI, exactly as it would freeze a server. Move heavy work to a `Worker`.
- While AppKit runs a tracking loop of its own (the user is holding a menu open, dragging a slider, or live-resizing a window), JavaScript timers and I/O callbacks pause; they run as soon as the gesture ends. UI callbacks the gesture itself causes (`onChange` while dragging a slider, `onResize` during the resize) still fire.
- A modal session begun through `objc` (`NSApp.runModalForWindow_()`, an `NSAlert` or open panel's `runModal()`) is such a loop for as long as it lasts: the call returns when the session ends, and no timer, I/O callback, immediate or promise continuation runs before then, wherever the call was made from. Prefer the sheet and completion-handler forms (`beginSheetModalForWindow:completionHandler:`, `-[NSSavePanel beginWithCompletionHandler:]`), which return at once and call back.

Process lifetime follows the usual rule: open windows keep the process alive; when the last one closes and nothing else is pending, `beforeExit` / `exit` fire and the process ends. Set `app.keepAlive = true` for menu-bar style tools that should outlive their windows. A quit (Cmd-Q, the Dock, logout, `app.quit()`) that nothing vetoes closes every window and exits as described under [the `app` object](#the-app-object).

An Objective-C exception raised inside a message sent through [`objc`](#the-objective-c-bridge) becomes a JavaScript error; one raised anywhere else that nothing catches ends the process, and the crash report is preceded by `error: uncaught Objective-C exception <name>: <reason>`.

`bun --hot` is not supported with `bun:appkit`: the app, its windows and its menu live for the whole process, so a reload would add a second set next to the first. Use `bun --watch`, which restarts the process.

## Testing

Each view and window can render itself to PNG with `snapshot()`, `button.click()` triggers the real action, `view.frame` is current after every change, and readable props (`value`, `checked`, `selectedIndex`, ...) reflect control state, so UI logic is testable by driving the objects directly. Without a display (plain `ssh`, CI agents, sandboxes) everything still runs off screen: windows lay out, controls fire, snapshots render; they are just never shown. `app.hasDisplay` tells you which case you are in. `"ERR_APPKIT_UNAVAILABLE"` is only thrown if the system frameworks cannot be loaded at all.

The application, its windows and `app`'s listeners are process-wide and `bun test` does not reset them between files, so a window a failed test leaves open is still in `app.windows` for the next file, and an unvetoed quit ends the whole run. The pattern that isolates tests is a small script per scenario that prints what it observed, run as a subprocess:

```ts counter.fixture.ts icon="/icons/typescript.svg"
import { app, Window, Button, Text, VStack } from "bun:appkit";

app.activationPolicy = "accessory"; // no Dock icon
const label = new Text({ text: "0" });
const button = new Button({ title: "+", onClick: () => (label.text = String(Number(label.text) + 1)) });
const win = new Window({ content: new VStack({ children: [label, button] }) });
button.click();
button.click();
console.log(JSON.stringify({ text: label.text, width: button.frame.width }));
win.close(); // nothing keeps the process alive after this
```

```ts counter.test.ts icon="/icons/typescript.svg"
import { test, expect } from "bun:test";

test("counter increments", async () => {
  await using proc = Bun.spawn({ cmd: ["bun", "counter.fixture.ts"], cwd: import.meta.dir, stdout: "pipe" });
  const result = JSON.parse(await proc.stdout.text());
  expect(result.text).toBe("2");
  expect(result.width).toBeGreaterThan(0);
  expect(await proc.exited).toBe(0);
});
```

Driving views inside the test process itself also works for quick checks; close every window you open (`for (const w of app.windows) w.close()` in `afterEach`) and do not call `app.quit()` there.

## The Objective-C bridge

`objc` is what the classes above are written with, and it reaches everything they do not cover: any Objective-C class and selector by Apple's own names, so the module is never a dead end. In numbers: the 25 curated elements are made of 30 AppKit and Foundation classes; the bridge reaches the roughly 770 classes, 280 protocols and 15,600 selectors that Foundation, AppKit, QuartzCore, Metal and MetalKit declare in a current macOS SDK (about a third of AppKit's `NSView` subclasses have a curated element; every other one is an `objc.classes.X` away), `objc.enums` knows 580 enumerations with 3330 members plus 833 loose constants, and the only Objective-C compiled into `bun` for all this is 44 classes and 169 selectors of typed bindings for the app lifecycle, `MetalView`, `gpu` and the bridge itself (`bun scripts/appkit-coverage.ts` in the Bun repository prints the breakdown against the installed SDK). It does not need the app to be running (Foundation classes work in a plain script), and it works in a `Worker` for everything except AppKit's UI classes; see [Threads and Workers](#threads-and-workers).

```ts
import { objc, VStack, Window } from "bun:appkit";

const { NSString, NSMutableArray, NSProcessInfo } = objc.classes; // any class by name; an unknown name throws a TypeError
const s = NSString.stringWithString_("hi"); // a JavaScript string is boxed to NSString where an object is expected
s.length(); // 2
s.UTF8String(); // "hi"
const list = NSMutableArray.new();
list.addObject_(s);
list.count(); // 1
`${NSProcessInfo.processInfo().processName()}`; // objects come back as handles; `${}` / String() gives -description

const win = new Window({ title: "t", visible: false });
win.native.setTitle_("u"); // .native is the NSWindow; win.title now reads "u"
win.native.frame(); // { origin: { x, y }, size: { width, height } }
win.native.setFrame_display_({ origin: { x: 0, y: 0 }, size: { width: 300, height: 200 } }, true);
new VStack().native.isKindOfClass_(objc.classes.NSStackView); // true
```

Every property of such a handle is a method that sends the selector of the same name, spelled PyObjC style: each `_` stands for a `:`, and the call takes exactly as many arguments as there are colons (`setFrame_display_(rect, true)` sends `setFrame:display:`, `count()` sends `count`). Leading underscores are kept (`_isKeyWindow()`), and `__` inside a name is a literal `_`. Reading a property sends nothing; calling it does. `handle.msgSend("setFrame:display:", rect, true)` takes the selector spelled the Objective-C way instead. A selector the receiver does not respond to, a wrong argument count and a value that does not fit the argument's type are `TypeError`s; nothing is sent in those cases.

`objc.js(handle)` converts Foundation values the other way (`NSString` to string, `NSNumber` to number or boolean, `NSData` to a `Uint8Array` and `NSDate` to a `Date` (both copied), `NSArray` and `NSDictionary` element by element, `NSNull` to `null`; anything else stays a handle), `objc.ns(value)` boxes a JavaScript value (a `Date` as `NSDate`, an `ArrayBuffer` or typed array as `NSData`), and `handle[objc.pointer]` is its address as a `bigint`. `objc.NSNotFound` is the `bigint` `9223372036854775807n` that `indexOfObject:`, `rangeOfString:` and similar lookups return for no match; every integer result above 2^53 is a `bigint`, so `===` against it is exact. A `View` or `Window` is not a handle: pass its `.native`. A `const char *` result is read as a C string; a method documented to return a pointer to bytes that are not text (declared `const char *` rather than `void *`) is not usable this way.

One object has one handle for as long as your program can reach the handle, so `===` compares objects (`win.native === win.native.contentView().window()`; `objc.same(a, b)` is the same test) and a class always comes back as its `objc.classes` handle. That one handle is shared by everything that refers to the object, and it counts how many times the bridge has handed the object out: each result that produces it (a send's, an out-parameter's, `objc.ns()`) is one acquisition, and `handle.release()` (or `using handle = …`, which releases at the end of the block) gives one back. With the last one the handle ends for every variable that holds it, anywhere in the program, and the next message that returns the object mints a fresh handle. So `using item = list.firstObject()` gives back only what that read acquired, while `release()` on the sole result of `alloc().init…()` or `objc.target()` ends the object's handle there and then. The receiver and arguments of a callback (a block's, a defined method's) are the caller's for the call and count as no acquisition, and what the windows and views of this module read for their own use (a view's layer or window, a shared colour, `NSApp`) they give back, so your count is your own reads; only the AppKit object a `Window` or view is built on is also held by it. `console.log(handle)` and `util.inspect` print `[objc ClassName: description]`; `"count" in handle` tells whether the object responds to that selector; `Object.keys(handle)` lists the selectors its class chain implements, spelled as properties; and the Foundation collections work with `for…of`, spread and `Array.from`: an `NSArray`, `NSSet` or `NSOrderedSet` yields its objects (as handles), an `NSDictionary` its keys, an `NSIndexSet` its indexes, an `NSEnumerator` (`reverseObjectEnumerator()`) whatever it has left.

```ts
const list = objc.ns(["b", "a"]);
for (const item of list) console.log(`${item}`);
const sorted = [...list.sortedArrayUsingSelector_("compare:")].map(objc.js); // ["a", "b"]
console.log(list); // [objc __NSArrayM: (b, a)]
```

Ownership follows Cocoa's rules for you: a handle keeps its object retained until it is garbage collected (or until you call `handle.release()`, after which the handle throws); results of `alloc`, `new`, `copy` and `mutableCopy` are taken over rather than retained again, and an `init…` consumes the `alloc()` handle it was called on (using that handle afterwards throws). The `alloc` itself is only sent when the `init…` is (or, for a class cluster such as `NSAttributedString` whose instances alone know their `init…` methods, when the first `init…` is looked up), so an `init…` whose arguments are wrong leaves nothing initialised behind, and an `alloc()` result accepts nothing but an `init…` until one succeeds. `NSString.alloc().initWithUTF8String_("x")` therefore neither leaks nor over-releases. The `retain`, `release` and `autorelease` selectors themselves are refused, and so is `NSAutoreleasePool` (every send already runs inside a pool). A window that comes back from an `init…` or `new…` message, or from any class method of `NSWindow` or a subclass (`NSWindow.windowWithContentViewController_(vc)`, `NSSavePanel.savePanel()`), is sent `setReleasedWhenClosed:NO` right after, because AppKit's default for a window made in code would release it a second time when it closes; the handle therefore stays valid after `close()`.

Receivers that are `NSProxy` instances (such as the one `-[NSUndoManager prepareWithInvocationTarget:]` returns) work: the bridge asks them only `methodSignatureForSelector:` before sending, never `respondsToSelector:`, so the message you send is the first one the proxy sees. A selector the proxy has no signature for is a `TypeError` when the proxy answers `nil` (NSUndoManager's does) and an `ERR_OBJC_EXCEPTION` error when the proxy raises (`NSProxy`'s own `methodSignatureForSelector:` does). `objc.js()` leaves a proxy as a handle.

`window.native` is the `NSWindow` and `view.native` the widget's outer `NSView`: for `ScrollView`, `Table` and `TextEditor` that is the `NSScrollView` (`.documentView()` reaches the `NSTableView` or `NSTextView`); for `Group` it is the `NSBox`, whose children sit in an `NSStackView` inside its `contentView()`; for `MetalView` it is the `MTKView`, or a plain `NSView` when Metal is unavailable. Changes made through them show up in the curated properties that read the live object (`title`, `width`, `value`, `checked`, ...). A closed window's `.native` is still its `NSWindow`.

Not supported yet: pointer arguments that are not out-parameters or one of the Core Graphics objects above (`void *`, pointers to pointers or to other opaque structs, C arrays and buffers) other than `null`, structs and unions that contain an array, a bit-field, a pointer or a `long double` (or exceed 128 bytes), SIMD vector types, and variadic methods; those throw a `TypeError` naming the type. A block object cannot be sent messages, since `NSInvocation` would call the block instead; it can be passed as an argument, released, and called: `block.invoke(...args)` calls it with arguments converted by the type signature the block was compiled with (every block clang builds records one; one without is a `TypeError`), whether the block came from `objc.block()` or from a framework (`expression.expressionBlock()`, a `completionHandler` a delegate method receives). Variadic selectors (`stringWithFormat:`, `arrayWithObjects:`, `dictionaryWithObjectsAndKeys:`, anything taking a `va_list`) would read arguments the bridge has no way to pass, so they are refused: every method the macOS SDK headers declare with `...` or a `va_list` parameter, on the declaring class and its subclasses; use `stringWithString:`, `objc.ns([...])`, `objc.ns({...})` or `predicateWithFormat:argumentArray:` instead. `performSelector:`, `performSelector:withObject:` and `performSelector:withObject:withObject:` are refused too: they are declared to return an object whatever the performed method returns, so the result cannot be converted safely; send the selector itself (`receiver.msgSend(name, ...args)` when the name is in a variable).

An Objective-C exception raised inside a method you call (`list.objectAtIndex_(99)`, `dict.setObject_forKey_(null, "k")`) is caught where the message was sent and thrown as an `Error` with `code` `"ERR_OBJC_EXCEPTION"`: `name` is the `NSException` name (`"NSRangeException"`), `message` its reason, `userInfo` its `userInfo` dictionary printed when there is one, and `exception` a handle on the `NSException` itself. The process carries on, and whatever the method did before raising stays done. Exceptions raised anywhere else (inside AppKit while it dispatches an event, say) are not caught and end the process as described under [Event loop](#event-loop).

```ts
try {
  objc.classes.NSArray.array().objectAtIndex_(3);
} catch (e) {
  e.name; // "NSRangeException"
  e.message; // "*** -[__NSArray0 objectAtIndex:]: index 3 beyond bounds for empty array"
}
```

In TypeScript, the classes `bun:appkit` builds on and the common Foundation and AppKit ones are declared with their methods, generated from the SDK headers: `objc.classes.NSWindow` completes its class methods, what they return is an `objc.NSWindow` (also the type of `window.native`; `button.native` is an `objc.NSButton`) with the instance methods of `NSWindow` and its superclasses, each taking one argument per colon and typed the way the table above converts it (an `NSString *` parameter takes a string or a handle, a `BOOL` a boolean, an `NSRect` a `Rect` or `{ origin, size }`, a block a function where the bridge knows its type, an `NS_OPTIONS` parameter its `objc.enums` members), `for...of` over an `objc.NSArray` yields handles, and `objc.enums.NSWindowStyleMask` lists its members. The delegate and data-source protocols are declared too (`objc.protocols.NSWindowDelegate`), with their `@optional` methods optional: test `"windowShouldClose_" in delegate` before calling one (`?.()` would still send, since every selector reads as a function). Any other class is a plain `ObjCObject`, and a selector the declarations lack still type-checks through the index signature as before.

### Out-parameters

Where a method takes a pointer to a value it fills in (`NSError **error`, `BOOL *isDirectory`, `double *result`, `NSRangePointer`), pass `objc.out()` and read its `.value` after the call, or pass `null` for `NULL`; out-parameters at the end of the argument list may simply be left off, which passes `NULL`. `objc.out(initial)` (or a plain `{ value: initial }`) sets what the storage holds going in, for the methods that read it; unset, it holds zero / `nil`. What comes back in `.value` is converted like a result of the pointed-to type: an `NSError` as a handle (`null` when the method left it `nil`), a `double` as a number, an `NSRange` as `{ location, length }`.

`objc.out()` is storage for one value. A parameter that is a C array or buffer the method reads or fills element by element (`-[NSArray getObjects:range:]`, `-[NSString getCharacters:range:]` and `getCString:maxLength:encoding:`, `-[NSIndexSet getIndexes:maxCount:inIndexRange:]`, `+[NSArray arrayWithObjects:count:]`, `-[NSColor getComponents:]`, `-[NSInputStream read:maxLength:]`) accepts only `null`, and anything else is a `TypeError`: the bridge cannot size such a buffer, so allocate it with `bun:ffi` and call the method through `bun:ffi` instead. Those parameters are the ones the macOS SDK headers declare as arrays (`id objects[]`, or a pointer next to a `count:`, `length:`, `range:` or similar part), every `const` pointer to values (`const CGFloat *`), and every `char *` that is not `const`.

```ts
const { NSFileManager, NSScanner } = objc.classes;

const error = objc.out();
const attributes = NSFileManager.defaultManager().attributesOfItemAtPath_error_("/nope", error);
if (attributes === null) console.log(`${error.value.domain()} ${error.value.code()}`); // NSCocoaErrorDomain 260

const value = objc.out();
NSScanner.scannerWithString_("6.5").scanDouble_(value); // true
value.value; // 6.5

const isDirectory = objc.out();
NSFileManager.defaultManager().fileExistsAtPath_isDirectory_("/tmp", isDirectory); // isDirectory.value === true
```

A block or a [defined method](#defining-classes-delegates-data-sources-targets) called with such a pointer receives the same kind of object: `.value` holds what the caller's storage holds for numbers, booleans and structs, and starts `null` for an out-only object pointer (`NSError **`: the caller need not have initialised it) but holds the caller's object for one declared `inout` (`N^@`: KVC's `validateValue:forKey:error:`, a formatter's partial-string pointer); whatever the function leaves in `.value` is stored back when it returns (an object stored through `NSError **` is autoreleased, as the convention requires). A `NULL` pointer arrives holding zero and stores nothing.

### Constants and enums

`objc.constants` reads the constants the loaded frameworks export as globals (AppKit, Foundation and what they link first, then anything else the process has loaded, such as a framework brought in with `NSBundle`), by name, each time it is read: the `NSString` keys, notification names and run-loop modes (`objc.constants.NSFontAttributeName`, `NSWindowDidResizeNotification`, `NSDefaultRunLoopMode`) come back as handles, and the numbers and structs Foundation and AppKit declare (`NSFontWeightBold`, `NSViewNoIntrinsicMetric`, `NSZeroRect`, `NSUnderlineByWordMask`, and the CoreFoundation, CoreGraphics and C library numbers their headers include, such as `kCFAbsoluteTimeIntervalSince1970` or `vm_page_size`) as numbers and objects. Any other name is read as an object after a check that what the global holds is one (nil, or a pointer whose class the runtime knows); a global that holds something else (a `double` from another framework, a struct of callbacks) is a `TypeError` telling you to give its type: `objc.constant(name, { type: "d" })` reads a `double` (`"q"` `NSInteger`, `"Q"` `NSUInteger`, `"B"` `BOOL`, `"{CGSize=dd}"` a struct), `objc.constant("kCAAnimationRotateAuto")` an object. An unknown name, or the name of a function (`NSBeep`, `NSClassFromString`), is a `TypeError` as well; an explicit type that is wrong reads garbage, as it would in C.

`objc.enums` has every `NS_ENUM`, `NS_OPTIONS` and `NS_CLOSED_ENUM` of Foundation, AppKit, QuartzCore, Metal and MetalKit by type name, each with its members under Apple's name less the shared prefix, first word in lower case (`objc.enums.NSWindowStyleMask.titled`, `NSEventType.leftMouseDown`, `NSBitmapImageFileType.png`, `NSLineBreakMode.byWordWrapping`, `MTLPixelFormat.bgra8Unorm`) and under the full name (`NSWindowStyleMask.NSWindowStyleMaskTitled`); and, flat, every member, every constant of an unnamed enum and every `static const` number of those headers (`objc.enums.NSWindowStyleMaskTitled`, `NSUTF8StringEncoding`, `NSModalResponseOK`, `NSControlStateValueOn`, `NSUpArrowFunctionKey`, `NSLayoutPriorityRequired`). Values are plain numbers (`bigint` above 2^53) generated from the macOS SDK, so architecture-dependent ones (`NSTextAlignment.center`) are right for the running binary; the enum objects are frozen and list both spellings in `Object.keys()`.

```ts
const { NSPanel, NSNotificationCenter } = objc.classes;
const { NSWindowStyleMask, NSBackingStoreType } = objc.enums;
const mask = NSWindowStyleMask.titled | NSWindowStyleMask.closable | NSWindowStyleMask.resizable;
const panel = NSPanel.alloc().initWithContentRect_styleMask_backing_defer_(
  { x: 0, y: 0, width: 300, height: 120 },
  mask,
  NSBackingStoreType.buffered,
  false,
);
const label = new Text({ text: "centered" });
label.native.setAlignment_(objc.enums.NSTextAlignment.center);
NSNotificationCenter.defaultCenter().addObserverForName_object_queue_usingBlock_(
  objc.constants.NSWindowDidResizeNotification,
  panel,
  null,
  note => console.log(`${note.name()}`),
);
```

### Blocks: completion handlers and callbacks

Where a method takes a block, pass a JavaScript function. The bridge knows the block's type for every block parameter of the Foundation, AppKit, QuartzCore, Metal and MetalKit methods in the macOS SDK (from the BridgeSupport metadata macOS ships, plus the block-typed properties in those headers), so a function is enough wherever that type is one it can call a function through (the table below); anywhere else (another framework, a type outside the table) make the block yourself with `objc.block(fn, types)`, where `types` is the block's Objective-C type encoding: the return type, `@?` for the block itself, then one code per argument, or the `TypeError` names the type the method wants. A block made that way is a handle like any other and can be passed to any number of methods. Where the bridge knows the method's block type, a block from `objc.block()` of a different type is a `TypeError`; anywhere else `types` must match the method's block parameter exactly, as the block's declaration must in C, and a mismatch is undefined behaviour (a crash, or worse).

```ts
const { NSOperationQueue, NSExpression } = objc.classes;
const list = objc.ns(["b", "a", "c"]);

list.enumerateObjectsUsingBlock_((obj, index, stop) => {
  console.log(index, objc.js(obj));
  if (index === 1) stop.value = true; // BOOL *stop
});
const sorted = list.sortedArrayUsingComparator_((a, b) => `${a}`.localeCompare(`${b}`)); // NSComparator returns NSComparisonResult
const matches = list.indexesOfObjectsPassingTest_((obj, index, stop) => `${obj}` !== "b"); // BOOL return
NSOperationQueue.mainQueue().addOperationWithBlock_(() => console.log("next run loop turn"));
panel.beginWithCompletionHandler_(response => console.log(response === 1 ? `${panel.URL()}` : "cancelled"));

// A method the bridge has no block type for: spell it out.
const expr = NSExpression.expressionForBlock_arguments_(
  objc.block((object, expressions, context) => `got ${objc.js(object)}`, "@@?@@@"),
  [],
);
```

The function runs on the thread that made the block, inside whatever calls it: synchronously inside your own call for enumerations and comparators, or, for a block the main thread made, later from the main run loop for completion handlers, timers and the main operation queue, which therefore only run once the application has started (a `Window` exists, `app.keepAlive` was set, or `app.activate()` was called); a `Worker` has no run loop, so a block made there only ever runs synchronously (see [Threads and Workers](#threads-and-workers)). Arguments arrive converted as message results are (objects as handles); a `BOOL *` argument (the `stop` flag of an enumeration) arrives as an object whose `value` you can set to `true`. The return value is converted as a message argument of the block's return type would be. If the function throws, or returns something that does not fit, that is reported as an uncaught JavaScript error, the caller receives `0` / `NO` / `nil`, and any `BOOL *stop` is set so an enumeration ends. A block called on any other thread (a background queue's operation, `NSOperation`'s `completionBlock`, or the main thread for a block a `Worker` made) does not run the function and returns zero there, and an uncaught error naming the block's type is reported on the block's thread. `objc.block(fn)` without `types` makes a block returning `void` whose arguments are all objects, one per parameter `fn` declares. The block keeps `fn` alive for as long as anything retains the block (your handle, or the framework that copied it); a type encoding that does not parse, or is not in this table, is a `TypeError`:

| encoding              | C type                                    |
| --------------------- | ----------------------------------------- |
| `v@?`                 | `void (^)(void)`                          |
| `v@?@`                | `void (^)(id)`                            |
| `v@?@@`               | `void (^)(id, id)`                        |
| `v@?@@@`              | `void (^)(id, id, id)`                    |
| `v@?B`                | `void (^)(BOOL)`                          |
| `v@?q`                | `void (^)(NSInteger)` (`NSModalResponse`) |
| `v@?Q`                | `void (^)(NSUInteger)`                    |
| `v@?d`                | `void (^)(double)`                        |
| `v@?@B`               | `void (^)(id, BOOL)`                      |
| `v@?@q`               | `void (^)(id, NSInteger)`                 |
| `v@?@Q`               | `void (^)(id, NSUInteger)`                |
| `v@?@d`               | `void (^)(id, double)`                    |
| `v@?@@q`              | `void (^)(id, id, NSInteger)`             |
| `v@?@^B`              | `void (^)(id, BOOL *)`                    |
| `v@?Q^B`              | `void (^)(NSUInteger, BOOL *)`            |
| `v@?@Q^B`             | `void (^)(id, NSUInteger, BOOL *)`        |
| `v@?@@^B`             | `void (^)(id, id, BOOL *)`                |

### Defining classes: delegates, data sources, targets

`objc.defineClass()` registers an Objective-C class whose instance methods are JavaScript functions, so AppKit can call your code: a table's data source, a window's delegate, a control's target, or a subclass that overrides a framework method. It returns the class; instances come from `.new()` or `.alloc().init…()` like any other, and are ordinary handles.

```ts
import { objc } from "bun:appkit";
const { NSTableView, NSTableColumn } = objc.classes;

const rows = ["alpha", "beta", "gamma"];
const DataSource = objc.defineClass({
  name: "RowsDataSource", // optional; must be free; also reachable as objc.classes.RowsDataSource
  protocols: ["NSTableViewDataSource"], // conformsToProtocol: answers YES; types the methods below
  methods: {
    "numberOfRowsInTableView:": () => rows.length,
    "tableView:objectValueForTableColumn:row:": (_table, _column, row) => rows[row],
  },
});
const dataSource = DataSource.new();
const table = NSTableView.alloc().initWithFrame_({ x: 0, y: 0, width: 200, height: 100 });
table.addTableColumn_(NSTableColumn.alloc().initWithIdentifier_("name"));
table.setDataSource_(dataSource); // weak: keep `dataSource` referenced yourself
table.reloadData();

// Overriding a superclass method: the encoding is read off NSView. A method
// whose answer never changes takes the answer itself: no JavaScript runs.
const Flipped = objc.defineClass({
  superclass: "NSView",
  methods: { isFlipped: true, "mouseDown:": event => console.log(`${event}`) },
});

// A selector nothing declares needs its encoding spelled out.
const Doubler = objc.defineClass({
  methods: { "twice:": { types: "q@:q", fn: n => n * 2 } },
});

// A control target in one line; the action selector is "action:".
const target = objc.target(sender => console.log(`clicked ${sender}`));
button.setTarget_(target); // weak as well
button.setAction_("action:");
```

Methods are keyed by selector, written with colons (`"tableView:objectValueForTableColumn:row:"`) or with underscores the way sends spell them (`tableView_objectValueForTableColumn_row_`); a function that declares more parameters than the selector has colons is a `TypeError`. A method given as a constant instead of a function (a boolean, a number or `null`, bare or as `{ types, value }`) is a native method that returns that value, callable on any thread and costing no call into JavaScript; the value must fit the return type (`true` for a `BOOL`, a number for a numeric type, `null` for an object or pointer), else a `TypeError`. Each one's Objective-C type encoding is, in order: the `types` you give (`{ types: "v@:@", fn }`: return type, then `@:` for the receiver and `_cmd`, then one code per argument); what a listed protocol declares for that selector (required or optional); what the superclass chain implements for it; what the protocols of Foundation, AppKit, QuartzCore and Metal declare for it when a class lists none (`numberOfRowsInTableView:` is typed right without naming `NSTableViewDataSource`; a selector they declare in conflicting ways is a `TypeError` asking for `protocols` or `types`); otherwise an object return and object arguments, one per colon. Every protocol those frameworks' headers declare can be listed, including the ones no framework registers at run time (`NSTextFieldDelegate`'s relatives `NSTokenFieldDelegate` and `NSStackViewDelegate`, `MTKViewDelegate`), which the bridge registers from the SDK's description on first use. The class really has these methods, so `respondsToSelector:`, `instancesRespondToSelector:`, `methodSignatureForSelector:` and `conformsToProtocol:` (with `objc.protocols.NSTableViewDataSource`, a `Protocol` handle by name) all answer truthfully, and a method with a superclass implementation is overridden. Listing a protocol without defining (or inheriting) every method it marks required is a `TypeError`; optional methods stay optional. There are no `super` calls and no class methods, so `init…` methods cannot be defined either (create the object with the superclass's initializer and set it up afterwards); nor can the reference-counting methods (`retain`, `release`, `autorelease`, `retainCount`, `allowsWeakReference`, `retainWeakReference`), `dealloc`, `forwardInvocation:` or `methodSignatureForSelector:`. A subclass of a defined class inherits its methods and may override them.

A method runs on the thread that defined the class, synchronously, inside whatever sent the message: AppKit dispatching an event while the app runs, or your own bridged call (`table.reloadData()` above asks the data source before it returns). `this` is the receiver's handle; arguments arrive converted as the results column of the table above describes (objects stay handles; use `objc.js()`; an out-parameter as an object whose `.value` you set), and the return value is converted as the pass column describes for the method's return type (`undefined` is `nil` for an object return). A block argument (a `completionHandler` AppKit passes) arrives as a handle to call with `.invoke(...args)`; a block return takes a handle from `objc.block()`. `char *` or other pointer returns are not supported in defined methods. An invocation handed to `forwardInvocation:` by hand whose signature is not the method's is refused the same way a throw is. If the function throws, or returns a value that does not fit the return type, that is reported as an uncaught JavaScript error (`process.on("uncaughtException")` sees it) and the sender receives `0`, `NO` or `nil`; it never becomes an Objective-C exception. A message that reaches the object on another thread than the one that defined the class, or that a superclass's `dealloc` sends while the object is being destroyed, is not delivered to JavaScript and returns zero there; the first kind is reported as an uncaught error naming the method, on the defining thread.

A defined class lives for the rest of the process, and so do its methods and everything they close over: define classes once, at module scope, not per window or per component (and not in a `Worker` spawned per task: every Worker that runs the definition registers its own class; see [Threads and Workers](#threads-and-workers)). Only the function given to `objc.target()` belongs to its object and is let go when that object deallocates; all targets share one class. AppKit holds nearly every delegate, data source and target zeroing-weak, so keep the handle referenced (a variable, a property on your view object) for as long as AppKit should call it; once the handle is garbage collected or released and nothing else retains the object, it is gone, the property reads `nil` and the control silently stops firing. A few properties are still declared `assign` (a plain pointer: `NSXMLParser.delegate`, `NSComboBox.dataSource`, `NSCache.delegate`, `NSKeyedArchiver.delegate`, `NSTextFinder.client` among them); for those the bridge has the receiver hold the object you set until you set another or `null`, so a collected delegate cannot leave it pointing at freed memory. The reverse holds too: while an `objc.target()` object lives, its function stays reachable from it, so a target whose function closes over the object that keeps the target's handle is a cycle the collector cannot break; `release()` the handle when that part of the interface goes away.

### Threads and Workers

In a `Worker`, `objc` works as it does on the main thread for Foundation and for the parts of AppKit that are not user interface: strings, collections, `NSFileManager`, `NSUserDefaults`, `NSJSONSerialization`, `NSData`, `NSDate`, `NSImage`, `NSColor` and so on. The frameworks load once for the process from whichever thread touches them first, and Cocoa is put in multithreaded mode (`NSThread.isMultiThreaded()` is true) before any script uses them. Each thread keeps its own state: its own handles (the same object, `NSProcessInfo.processInfo()` say, is a different handle object in each thread and `===` only within one), its own `objc.classes` and `objc.constants` caches, an autorelease pool around every call, and its own defined classes and blocks.

Off the main thread the bridge checks the receiver of every message, never its arguments or result. Sending to, allocating, or giving `objc.defineClass` as `superclass` a class the AppKit headers mark main-thread-only (`NS_SWIFT_UI_ACTOR`: `NSResponder`, and with it `NSView`, every control, `NSWindow`, panels, `NSApplication`, view and window controllers and `NSPopover`; `NSCell`; `NSAlert`; `NSToolbar`, `NSTouchBar` and their items; `NSTableColumn`; `NSDocument` and `NSDocumentController`; gesture recognizers; collection-view, grid and scrubber layout objects; the print, page-layout and PDF panels and `NSPrintOperation`; `NSHelpManager`, `NSTextPreview`, `NSSliderAccessory`, `NSWritingToolsCoordinator`), or `NSMenu`, `NSMenuItem`, `NSStatusBar`, `NSStatusItem`, `NSNib`, `NSStoryboard` or `NSDockTile`, or a subclass of any of those, throws an `ERR_INVALID_STATE` error naming the class (`objc: NSWindow (a kind of NSResponder) can only be used on the process's main thread, not in a Worker: …`). The messages every object answers about itself (`class`, `superclass`, `isKindOfClass:`, `isMemberOfClass:`, `respondsToSelector:`, `conformsToProtocol:`, `isEqual:`, `hash`, `self`, `isProxy`, `className`, `description`, `debugDescription`) are let through, so a Worker handed a mixed collection can tell what is in it, and looking a class up in `objc.classes` is fine. What the check cannot see is yours to keep on the main thread, as in a native program: a method of an allowed class that builds or drives user interface (`NSWorkspace` opening panels, `NSTextInputContext`), or a window or view arriving as an argument to a Worker's block. The curated layer is main-thread-only outright: `app`, `Window`, every view, `MetalView` and `gpu` throw in a `Worker`.

A block made in a `Worker`, and the methods of a class defined in one, run only on that Worker's thread. Called anywhere else (a background queue, or the main thread) they return `0` / `NO` / `nil` to the caller and the Worker is sent an uncaught error naming the block or method, which ends the Worker unless it is handled (`process.on("uncaughtException")`), exactly as the main thread does for its own. A Worker runs no run loop and is no dispatch queue, so nothing asynchronous ever calls back on it: timers and run-loop sources scheduled from it (`NSTimer`, delayed performs, streams) never fire at all, and completion handlers, operation-queue and main-queue blocks and notification observers with a queue are called on other threads, where they are refused as just said. What does run a Worker's functions is whatever calls them synchronously inside one of the Worker's own sends: enumeration blocks, comparators, predicates, formatters, and delegate methods the send itself triggers. Use blocks and defined classes in a Worker for those only.

`objc.defineClass` registers a class for the whole process and nothing ever unregisters it. On the main thread the class gets the `name` you give, and a taken name is a `TypeError`; on any other thread it is registered as `name_<n>`, `n` numbering the threads that have used the bridge, so `objc.classes[name]` is the main thread's class whichever thread ran the module first, and `String(cls)` says what name a Worker's class got. Every Worker that evaluates a module-scope `objc.defineClass` therefore adds classes, and keeps their functions, for the life of the process: define classes in long-lived Workers, not in one spawned per task. `objc.target()` objects are all of one class whichever thread makes them, so they add nothing per Worker; each one's function runs on the thread that made it. A class one thread defined cannot be the `superclass` of a class another thread defines. When a Worker exits, everything it held is released, and the blocks and classes it defined stay registered but inert: whoever still holds one gets `0` / `NO` / `nil` from it, the first such call is noted once on stderr, and nothing touches the Worker's JavaScript heap after it has gone.

## Limitations

- macOS only (arm64 and x64). On other platforms `Bun.AppKit` is `undefined` and `bun:appkit` is not a builtin module, so importing it fails to resolve.
- The user interface runs on the main thread; there is no separate UI thread. `app`, `Window`, the views, `MetalView`, `gpu` and, through `objc`, the classes AppKit marks main-thread-only (responders, cells, alerts, toolbars, documents, …) plus menus, the status bar, nibs, storyboards and the Dock tile throw in a `Worker`; the rest of `objc` works there, for synchronous use, since a Worker has no run loop (see [Threads and Workers](#threads-and-workers)).
- Timers and I/O pause while a menu is open, a window is being live-resized or a modal session runs, and a long synchronous callback stalls the UI as it would any other.
- `bun --hot` is not supported; use `bun --watch`. Under `bun test --isolate` (which `--parallel` implies) each file loads `bun:appkit` afresh and the bridge moves to it; the application and any window an earlier file left open stay as they were. A second global object alive beside the main one on the same thread (a `ShadowRealm`) cannot load it: that throws.
- `bun build --compile` works: `bun:appkit` stays a builtin of the compiled executable, which needs macOS to run like any other use of it. A compiled executable has its own `NSUserDefaults` domain (its file name), so state AppKit keeps per application, such as a window's `restoreName` frame, is separate from what the same script saved when run with `bun`, where every script shares the `bun` domain.
- No curated modal APIs (`NSAlert`, open/save panels, sheets), drag and drop, or custom drawing other than through `MetalView` yet; `objc` reaches the underlying classes, within the limits listed above. No `.app` bundling: the program is a normal `bun` process, so it has the generic executable icon in the Dock unless `activationPolicy` is `"accessory"`.
